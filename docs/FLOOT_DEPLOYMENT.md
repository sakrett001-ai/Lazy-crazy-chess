# Белая пешка во Floot

Репозиторий: `sakrett001-ai/Lazy-crazy-chess`, исходная ветка `main`.
Проект Floot: `5311a72f-aeb2-4bc4-94ea-e491870d0b13`.
Адрес приложения: [lazy-crazy-chess.floot.app](https://lazy-crazy-chess.floot.app). Оболочка опубликована во Floot; её обновление выполняется отдельно от выпуска просмотрщика.

## Два независимых вида просмотра

`prototypes/white-pawn/white-pawn.html` — автономный HTML с моделью и изображением внутри. Он остаётся доступен для открытия без сети.

Размещённый просмотр — компактный HTML с интерфейсом и Three.js внутри. Модель и изображение он получает из этого же публичного репозитория по неизменяемому адресу конкретного коммита. Холодный запуск требует сети. Перед открытием GLB проверяется SHA-256; при несовпадении модель не запускается и непроверенный файл не предлагается для скачивания.

Файлы релиза: интерфейс `0.3.0`, модель `0.2.1`. Публикация этих файлов во Floot выполняется отдельно после полного цикла проверок; действующий релиз определяют manifest в `gh-pages` и строка версии на сайте. Клипы `Shield_Brace` («Упор щитом») и `Spear_Study` («Учебный укол») сохраняют имена и длительность по 4 с.

Для модели 0.2.0 прошли [структурная проверка](../prototypes/white-pawn/assets/model-checks.json) и [проверка движения экспортированных поверхностей](../prototypes/white-pawn/review/equipment-checks.json). [Бенчмарк 0.2](WHITE_PAWN_V02_BENCHMARK.md) задаёт отдельную приёмку брони и креплений; [аудит 0.1.0](WHITE_PAWN_REVIEW_2026-10-21.md) остаётся историей исходных дефектов. Проекция таза на контур подошв служит геометрическим показателем опоры, без расчёта центра масс и физического баланса. Продвижение копья наконечником вдоль оси подтверждает траекторию анимации, без моделирования сил удара. Проверки просмотрщика подтверждают загрузку, целостность и управление; аудит ремней и визуальную приёмку они не заменяют.

Версия интерфейса берётся из `prototypes/white-pawn/package.json`; версия модели задаётся `MODEL_VERSION` в `scripts/release-utils.mjs`. Автономный просмотр использует те же номера в `src/viewer.mjs`. Manifest и строка версии различают эти два номера; замечания дополнительно привязаны к точному SHA-256 GLB.

## Как приходит обновление

1. Изменения появляются в `main`.
2. `.github/workflows/publish-pawn.yml` устанавливает зависимости по lock-файлу `human-base`, проверяет снаряжение и движения конечного GLB (`verify:equipment`), выполняет тесты правил публикации, собирает и проверяет автономный просмотр и настройки снаряжения (`verify:appearance`).
3. `build:hosted` создаёт кандидат HTML без manifest релиза. `verify:hosted` проверяет загрузку, управление, экран 390 px, отказ при изменённом GLB и недоступном сервере, а также запасной режим без WebGL.
4. Только `release:hosted` создаёт `chess-release.json` со статусом `checks: passed`. Он требует успешные `review/appearance-checks.json`, `review/equipment-checks.json` и `review/geometry-checks.json`, каждый с `glbSha256`, совпадающим с SHA-256 текущего GLB, и сверяет остальные отчёты с точными SHA модели и обоих проверенных HTML. Workflow использует сохранённый в исходном коммите отчёт аудита геометрии и не запускает Blender для его создания; аудит не подтверждает физику боя или непрерывное отсутствие пересечений. Устаревшие или проваленные проверки не дают создать manifest.
5. Workflow повторно сверяет `main` с исходным коммитом и обычным fast-forward push добавляет в `gh-pages` только manifest и `chess/releases/<sourceCommit>/viewer.html`. Корневые страницы, прежние релизы и другие разделы не заменяются. PR проходят проверки без публикации.
6. Оболочка Floot получает manifest из `gh-pages`, проверяет его поля, размер и SHA-256 HTML. Просмотр запускается на домене Floot; сам GLB дополнительно проверяет браузер.

Это мост проверенных релизов. Изменение ядра просмотрщика не требует повторной публикации оболочки Floot. Изменения самой оболочки или её серверного обработчика нужно отдельно перенести и опубликовать через Floot. Текущая открытая страница не заменяет модель во время осмотра; новый релиз применяется после открытия или перезагрузки.

## Состав релиза

`gh-pages/chess-release.json` содержит `schemaVersion`, фиксированный `repository`, `sourceBranch: main`, полный `sourceCommit`, `version`, `modelVersion`, `checks`, `builtAt` и `document: {path, sha256, bytes}`.

HTML меньше 2 МБ и содержит `window.PAWN_HOSTED`: `modelUrl`, `modelSha256`, `posterUrl`, `version`, `modelVersion`, `sourceCommit`. URL модели и изображения закреплены за полным SHA коммита в `raw.githubusercontent.com`; ссылки на меняющуюся ветку не используются.

Бинарная модель и изображение не дублируются в `gh-pages`. Их исходные файлы остаются в `prototypes/white-pawn/assets/white-pawn.glb` и `prototypes/white-pawn/review/neutral.png` соответствующего коммита `main`.

## Локальная проверка

Из корня репозитория:

```bash
npm ci --prefix prototypes/human-base
cd prototypes/human-base
npx playwright install chromium
cd ../white-pawn
npm run test:release
npm run verify:equipment
npm run build
npm run verify
npm run build:hosted
npm run verify:hosted
npm run release:hosted
```

Выходные файлы находятся в `dist/` корня репозитория. `chess-candidate.json` и `dist/review/` — местные данные проверки; в опубликованный релиз они не входят. Перед окончательной сборкой исходники должны быть сохранены в коммите: адрес GLB проверяется против содержимого указанного коммита. Сам локальный запуск ничего не отправляет в GitHub или Floot.

Если проверка или workflow не прошли, ранее опубликованный manifest в `gh-pages` остаётся без изменений. Локальная неудачная сборка удаляет старый manifest из `dist/`, чтобы его случайно не приняли за новый проверенный релиз. Для возврата к прежнему поведению можно сделать обычный revert в `main` и провести его через тот же цикл.

Для модели 0.2.1 изменены только материалы. Аудит контактов перенесён с явной ссылкой на исходный отчёт и доказательством неизменности геометрии; [подробнее](WHITE_PAWN_CUSTOMIZATION.md).
